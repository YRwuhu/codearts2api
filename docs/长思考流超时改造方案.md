# 长思考流被 180s 截断：根因与改造方案

2026-11-09。针对 `读取上游流失败: error decoding response body`。

## 1. 现象

长思考模型（`kimi-k3.1-pro`，thinkingLevel=max）的流式请求在**整 180 秒**处被切断，
客户端收到 SSE error 帧：

```
data: {"error":{"message":"读取上游流失败: error decoding response body",...}}
```

`usage.jsonl` 侧同一条记录为 `upstream_network_error`、`elapsed_ms` 180002–180015、
`prompt/completion_tokens = 0`。

## 2. 根因

`src/chat.rs` 用 `RequestBuilder::timeout()` 实现"空闲读上限"：

```rust
// 注释写的是"空闲读取上限；不再限制整段流的总时长"
let mut request = state.http.post(TARGET).timeout(UPSTREAM_IDLE_TIMEOUT).body(body_bytes);
```

reqwest 0.13.5 的 `RequestBuilder::timeout` 文档原文是 *"applied from when the request starts
connecting until the response body has finished"*，实现为 `TotalTimeoutBody`（`reqwest/src/async_impl/body.rs`
278-326）：sleep 在 `execute_request` 里创建，deadline = send + 180s，**到点就把 body 流掐断**。
它不是空闲超时，而是整段流的总时长。

掐断后的错误被 `Response::bytes_stream()` 统一包成 `Kind::Decode`
（`reqwest/src/async_impl/response.rs:352` 的 `map_err(crate::error::decode)`），Display 只剩
`error decoding response body`，所以账本里看不出真因。

### 证据

| 证据 | 数值 |
|---|---|
| 成功记录中 `elapsed_ms` 最大值 | 169430（无一条 >170s，>179s 为 0） |
| 9 次长请求失败耗时 | 180002–180015 ms（超 180s 仅 2–6ms，等于 `started → send()` 的毫秒开销；若截止来自上游至少多一个 RTT） |
| 本会话三轮失败 | 思考字符 15738 / 16943 / 16709（≈87–94 字/秒，吞吐不同）但截止时刻几乎一致 ⇒ 由时钟而非内容决定 |
| 同模型 169.4s 成功 | 出现在 180s 失败前 4 分钟 ⇒ 该模型本来就常跑满 3 分钟 |

### 顺带确认的边界

- 三协议下游都已处理心跳：`chat::openai_sse_body` 发 `: keepalive`、`responses::stream_body` 发
  `: keepalive`、`anthropic::sse_body` 转 `event: ping`；客户端不会把长静默当死连接。
- 全仓没有 tower `TimeoutLayer`（grep-only 结论）。
- 图的盲点：`async_stream!` 宏内的调用没有 CALLS 边（`sse_stream` 里的
  `is_account_failure` 在 chat.rs:1258），涉及宏的接缝一律用 grep 复核。

## 3. 修改目标

1. 单次上游流**不再有总时长上限**，20~30 分钟的慢思考可以正常完成；
2. 仍能识别"真死流"：只按**每读空闲**判定，且每收到一帧即重置；
3. 错误可辨识：`upstream_ttfb_timeout` / `upstream_idle_timeout` / `upstream_network_error` 分开，
   日志带 reqwest 的 source 链；
4. 空闲超时**不打账号冷却**，只对该模型短退避。

## 4. 三档时限

| 阶段 | 上限 | 实现位置 | 超时行为 |
|---|---|---|---|
| 连接 | 30s | `main.rs` `connect_timeout`（已有） | 换号重试 |
| 发请求 → 响应头 | 120s | `chat::attempt`，`tokio::time::timeout` 包 `send()` | 零输出，`Retry{upstream_ttfb_timeout}`，可换号 |
| 流内每读 | 300s（重置） | `chat::decode_sse` 与 `chat::read_body` | `upstream_idle_timeout` + 模型冷却 |
| 整段流总时长 | **无** | —— | —— |

取值理由：kimi 思考增量实测稳定在 ~90 字/秒，5 分钟无任何字节只可能是连接卡死；
TTFB 120s 覆盖 prefill 抖动，而 SSE 响应头实际是立即返回的。

## 6. 准代码

```rust
// H1
/// 上游「发出请求到收到响应头」的上限；响应头之后不再限制总时长。
const UPSTREAM_TTFB_TIMEOUT: Duration = Duration::from_secs(120);
/// 上游流「连续多久没有读到任何字节」才算死流；每读到一帧即重置。
const UPSTREAM_IDLE_READ_TIMEOUT: Duration = Duration::from_secs(300);
/// 空闲超时后该模型退避多久；不打账号冷却。
const MODEL_IDLE_COOLDOWN: Duration = Duration::from_secs(60);

// H2
let mut request = state.http.post(TARGET).body(body_bytes);
let upstream = match tokio::time::timeout(UPSTREAM_TTFB_TIMEOUT, request.send()).await {
    Ok(Ok(r)) => r,
    Ok(Err(e)) => return Ok(Attempt::Retry { error: ApiError::new(StatusCode::BAD_GATEWAY,
        "upstream_network_error", format!("upstream error: {e}")), switch_account: true }),
    Err(_) => return Ok(Attempt::Retry { error: ApiError::new(StatusCode::GATEWAY_TIMEOUT,
        "upstream_ttfb_timeout", format!("上游 {} 秒未返回响应头", UPSTREAM_TTFB_TIMEOUT.as_secs())),
        switch_account: true }),
};

// H2b
async fn read_body(mut upstream: reqwest::Response) -> Result<Vec<u8>, ApiError> {
    let mut raw = Vec::new();
    loop {
        match tokio::time::timeout(UPSTREAM_IDLE_READ_TIMEOUT, upstream.chunk()).await {
            Err(_) => return Err(idle_timeout_error("上游响应体")),
            Ok(None) => return Ok(raw),
            Ok(Some(Ok(chunk))) => raw.extend_from_slice(&chunk),
            Ok(Some(Err(e))) => return Err(stream_read_error(&e, "上游响应体")),
        }
    }
}

// H3
let mut idle = Box::pin(tokio::time::sleep(UPSTREAM_IDLE_READ_TIMEOUT));
'read: loop { tokio::select! {
    chunk = bytes.next() => {
        idle.as_mut().reset(tokio::time::Instant::now() + UPSTREAM_IDLE_READ_TIMEOUT);
        /* 原有逻辑 */
    }
    _ = idle.as_mut() => { failure = Some(idle_timeout_error("上游流")); break 'read; }
    _ = ticker.tick() => yield DecoderEvent::Event(Ok(StreamEvent::Chunk(Value::Null))),
} }

// H4
fn stream_read_error(error: &reqwest::Error, what: &str) -> ApiError { /* is_timeout 分流 + source 链 */ }

// H5
if error.code == "upstream_idle_timeout" { gate.cool_model(&model, MODEL_IDLE_COOLDOWN.as_secs()).await; }
else if is_account_failure(&error.code) { gate.note_failure(&error.message).await; }
```

## 7. 状态迁移矩阵

| 现态 | 触发 | 目标态 | 移动符号 | 期望可观测 |
|---|---|---|---|---|
| 流中，字节持续 | 无 | 流中 | `decode_sse` | 20~30 分钟正常完成，客户端收到 `[DONE]` |
| 流中，≥300s 无字节 | idle 分支 | `Complete(Err upstream_idle_timeout)` | `decode_sse` → `sse_stream` → 三个协议适配器 | SSE error 帧 + `usage.jsonl` 失败记录 + 该模型 60s 冷却 |
| 响应头 >120s 未到 | TTFB 超时 | `Retry{upstream_ttfb_timeout}` | `attempt` → `run_for_model` | 未吐正文，可换号/重试；仍计账号失败 |
| 非流式响应体中 ≥300s 无字节 | idle 超时 | `Retry{upstream_idle_timeout}` | `read_body` → `attempt` | 可换号；模型冷却 |
| 上游主动 FIN 且无 `[DONE]` | `Ok(None)` | `upstream_incomplete_response` | `decode_sse` | 行为不变 |
| 客户端中途断开 | 流被 drop | 槽位释放 | `SlotGuard.drop` | 槽位立即归还（账本无记录，属既有缺口，不在本次范围） |

## 8. 验证

- 单测（`tokio::time::pause`，需给 dev-dependencies 加 `tokio` 的 `test-util`）：
  1. `long_stream_survives_past_the_old_total_timeout`：虚拟 1800s、每 30s 一帧，必须
     `Complete(Ok)` —— 正是能拦住本 bug 的回归测试；
  2. `idle_stream_reports_idle_timeout`：两帧后永久 pending ⇒ `upstream_idle_timeout`；
  3. 既有 `decoder_distinguishes_completion_from_truncation`、`probe_retries_only_before_any_output` 保持绿。
- `cargo test`（整仓）+ `cargo build --release`。
- 真机：kimi 长思考请求跑过 180s，`usage.jsonl` 出现 `elapsed_ms > 180000` 且 `ok:true`。

## 9. 不做 / 待实测

- 不改客户端级 `read_timeout`（H6）、不改 `admin::test_model`（H7）、不改 `ACQUIRE_TIMEOUT`（H8）。
- **上游是否允许 20~30 分钟 SSE 未证实**（账本只证到 169s）。这必须用一次真实长思考验证；
  若上游先掐断，代理层无解，只能另立方案（例如分段续写，代价是流式语义）——先测再定。
- 客户端断开时账本不落记录（`record_usage` 不执行），属既有可观测性缺口。

## 10. 实施记录（2026-11-09）

| 文件 | 改动 |

死流将永久占住槽位；现统一走 `read_body` 的每读空闲守卫。

   「上游是否允许 20~30 分钟 SSE」这次没被覆盖——半小时是任务整体时长，不是单条流时长。
2. **新超时路径真机零触发**：300 s 空闲守卫与 120 s TTFB 只有单测覆盖；真实死流未出现，
